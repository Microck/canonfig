# One `~/.canonfig/` folder replaces each harness's global configuration

Status: proposed (2026-11-03). Replaces the Machine Profile JSONC authoring model and the repository harness projection feature. Supersedes the sentence in ADR 0001 that makes the Machine Profile JSONC file the only source of truth.

## Context

Canonfig ships two engines that never meet:

- **Signed Machine Profile sync.** The Source hand-writes `profile.jsonc` with `file`, `directory`, `config`, `skill`, `tool` and `credential` resources whose targets are arbitrary paths (`src/domain/profile.ts:66-156`, `src/domain/resource.ts:24-64`). Target validation rejects `..`, NUL and globs but has no allowlist (`src/domain/profile.ts:1048-1097`). The author must know every harness's native path and format, and nothing stops a profile from targeting `~/.codex/auth.json`.
- **Repository harness projection** (`canonfig harness ...`, `src/harness-configuration/`, about 7,900 lines, 2,000 lines of tests). It compiles a repository's `.canonfig/harness.yaml` into project-local files for 16 harnesses, keeps ownership in `.canonfig/.harness-state.json`, and applies with in-memory snapshots only (`core/planner.ts:270-380`). Sync never triggers it (`docs/harness-configuration.md:3-7`).

What a user wants is neither. They have one personal agent setup (instructions, skills, rules, MCP servers, hooks, commands, subagents, settings, and the tools those need) and want every harness they use, on every machine, to use it globally. The adapters already know how to translate that setup per harness; they just write to the wrong place, and the sync engine that knows how to transfer, journal and roll back has no idea what a harness is.

## Decision

### 1. The Canonical Folder

`~/.canonfig/` is the authoring format. The signed Profile Revision stays the wire format.

```text
~/.canonfig/
  canonfig.jsonc        harness list, MCP, hooks, settings, tools, credentials, groups, schedule, local policy, resources
  AGENTS.md             global instructions
  rules/<id>.md         frontmatter: description, paths, activation
  skills/<name>/...     Agent Skills trees (SKILL.md)
  agents/<id>.md        subagents; frontmatter: description, model, tools, writable
  commands/<id>.md      slash commands; frontmatter: description, argumentHint
  hooks/...             scripts referenced by canonfig.jsonc hooks
  files/...             content of authored resources (section 11)
  local/                machine-local items and overlays (sections 8 and 11), never published, never replaced
  .backups/             takeover snapshots (section 6)
  .reviews/             private append-local adoption reviews (section 11)
  .runtime/             generated hook runner
  state.sqlite, setup.json, policy.json, canonfig.log, installers/, skills-sources.json
```

The compiler reads only the eight authoring entries at the top (an allowlist, not a denylist). Everything else under `~/.canonfig/` is machine-local by definition and never published, mirrored or replaced. The canonical model is the existing harness model (`src/harness-configuration/core/schema-types.ts:97-112`) minus `project`, with rules, agents and commands discovered from their directories instead of listed. YAML authoring is dropped; `canonfig.jsonc` is the one format, edited by hand or by the GUI's comment-preserving writer.

### 2. Roles

- **Source.** `canonfig source publish --reviewer <name>` compiles `~/.canonfig/` into a revision: one Profile Resource per item (`instructions`, `rules/<id>`, `skills/<name>`, `agents/<id>`, `commands/<id>`, `hooks/<id>`, `mcp/<name>`, `settings/<harness>`, `tools/<id>`, `credentials/<id>`, `resources/<id>`, one file item per file under `files/`, `harnesses`, `local-policy`). Files stay content-addressed blobs. Signing, sequence, idempotent republish, enrollment, group authorization, transport and blob ranges are unchanged.
- **Follower.** Sync fetches and verifies the revision as today, then (a) materializes the authorized items into its own `~/.canonfig/` as a managed mirror, with `canonfig.jsonc` rendered canonically from the authorized subset, and (b) projects mirror plus `local/` into its selected harnesses.
- **Projection runs on every machine.** On the Source, or a machine that is not enrolled, `canonfig sync` projects the local folder; on a Follower it projects the mirror. One planner, executor, journal and recovery path (architecture invariant 9). A run records either a Profile Revision id or the local folder digest.
- **One role per machine.** One `~/.canonfig/` cannot be both the folder a Source authors and another Source's read-only mirror, so a machine is a Source or a Follower, never both. The Source identity (`source init`) and the follower configuration (`follower enroll`, pending or complete) are the two role records. Creating the Source identity (`source init`, Source setup apply), `setup plan --role source`, scanning, publishing, serving, installing the Source service, inviting and revoking refuse while a follower configuration exists, naming the followed Source and `canonfig follower unenroll` as the way out. `follower enroll` (before the invitation is used) and `setup plan --role follower` refuse while a Source identity exists. `setup apply` checks the journal's role again before any item runs or `setup.json` changes, since the machine can change role after planning; a role conflict raised inside the source-init item is refused the same way, without recording the item. These early checks give the side-effect-free refusal and its message; the guarantee is the repository: saving either role record checks for the other inside the same `BEGIN IMMEDIATE` transaction, so two concurrent commands cannot both persist a role. An enrollment refused only at that save has already spent its invitation, so it is cancelled on the Source and the message says to ask for a new invitation (or names `canonfig source revoke` if the cancel failed). All exit 2 (usage or configuration, `MachineRoleConflictError`). No command removes the Source role: the recovery is to remove the Source service and move the folder aside, which keeps its authored items, identity and run journal for audit instead of deleting them. `source service status` and `source service remove` stay available on a Follower, since they only report or clean up.

One Source publishes one Machine Profile, the folder. Follower Groups provide per-machine variation.

### 3. Projection and ownership

Each adapter declares, per harness, its roots and a positive list of **owned surfaces**: whole files, whole directories, or key paths inside files the harness shares with its own state. Projection turns the canonical model into plan actions of three internal kinds that the executor already journals and rolls back: `file` (replace), `directory` (replace), `config` (merge on owned keys). Adapters produce the harness targets; the only other targets are the authored resources of section 11, which are bounded away from every harness.

- **Whole files and directories Canonfig writes are replaced**, unless `local.appendLocal` shares them with the machine (section 11). At takeover the prior content is snapshotted (section 6) and removed. Afterward the surface holds exactly the published items plus `local/` items.
- **Shared files are key-owned.** In `~/.claude.json`, `config.toml`, `opencode.json` and similar files, Canonfig owns only the listed keys (for example `mcpServers`). Every other key, including auth, trust and history, stays follower-owned and byte-preserved by the format codecs (`src/synchronization/config-*.ts`).
- **Drift rule is the existing three-way rule** (`docs/architecture.md`, skill drift rule): observed equals desired, nothing to do; observed equals last applied, update; otherwise Follower Drift, preserve and report. It applies to mirror files and to projected outputs. A foreign entry that appears in an owned directory after takeover is drift: kept and reported, never deleted by a scheduled run. A drifted mirror item holds its projections at their last applied state.
- **One location per harness per feature.** When a harness reads the shared `~/.agents/skills/`, its skills go there and its private skills directory is left alone. Alternative native locations Canonfig does not write are listed at takeover, not touched.
- **Unsupported features are reported, never approximated into the wrong file.** Examples: Cursor keeps user rules outside the filesystem; Hermes's `SOUL.md` is an identity, not instructions. Capability levels stay as today (`native`, `translated`, `lossy`, `unsupported`).
- **Hook runtime precedes harness outputs.** When hooks are configured, projection resources depend on the generated runner and registry. Followers preserve these dependencies alongside mirror and tool prerequisites so an early stop cannot leave an installed plugin without its runtime.
- **Hook runtimes are content-addressed.** Runner and registry filenames include the digest of the runner implementation and registry. A new projection cannot replace the registry an unchanged, drifted, or held consumer still uses; old versions retire only after consumer updates.
- **Held outputs keep their runtime.** When excluded or temporarily unavailable harnesses retain applied outputs, removing canonical hooks must not retire the runner or registry those outputs still reference.
- **Runtime retirement follows consumer updates and removals.** A drift or human-action stop must leave the runner and registry intact while any planned harness output still needs them.
- **Follower linked-file retirement follows consumer updates too.** Removed mirrored `hooks/` scripts and `rules/` documents remain while a consumer is held, and otherwise depend on planned harness updates and removals so drift cannot strand an installed plugin or instruction link.
- **Dropped config keys retain drift protection.** A revision replacing all owned keys must compare the previous keys against their applied values before removing them; a disjoint new key set is not a fresh takeover of the file.
- **Subagents default to read and search capabilities.** Omitting `tools` must not grant write or shell access. Explicit empty tool lists remain empty in generated Amp registrations, never unrestricted.
- **Generated Amp identifiers preserve distinct agent IDs.** Escape underscores and hyphens separately; `review-fast` and `review_fast` must register different callable tools.

### 5. Detection and selection

- **Installed** means the adapter's executable resolves through Canonfig's verifier search order (recipe install directories, `~/.local/bin`, then `PATH`), without spawning it. Generic names (Cursor's `agent`) also require the harness root to exist. A config root alone is evidence, not installation: `~/.gemini` is shared by the Antigravity CLI, App and IDE.
- **Source setup** detects installed harnesses and preselects them in `canonfig.jsonc` `harnesses`. The user edits the list before the first apply. The list is published.
- **Import before takeover.** Source setup offers a one-time, reviewed import of each selected harness's existing instructions, skills, rules, agents, commands and MCP servers into `~/.canonfig/`. The user picks what to keep; duplicates by name are listed for a choice. Declined items are still covered by the takeover snapshot.
- **Follower** projects `harnesses` ∩ installed ∩ not locally excluded. A listed harness that is not installed is reported in plan and status (`not-installed`); the run can still converge. An installed harness that is not listed is ignored. A harness installed later is taken over on the next run, with a snapshot.
- **Roots are pinned.** The root resolved at takeover (including `CODEX_HOME` and similar overrides) is recorded per harness. A later run, for example a scheduled run without the shell's environment, that resolves a different root stops with Human Action Required instead of projecting into a second location. Roots must resolve inside the user's home directory.
- **Applied surface paths are pinned too.** A newly appearing config alternative must not redirect an already-owned resource. If resolution differs from its Applied Resource Record, stop with Human Action Required before writes or backup capture.
- **Every surface stays inside home.** Validate each resolved output path, not only the harness root: environment overrides can place individual plugin surfaces elsewhere. Snapshot capture independently rejects external targets and copy paths that escape the snapshot directory.
- **Removing a harness from the list** retires its unmodified owned outputs through the normal removal path. It does not restore the snapshot; `canonfig restore` does that explicitly.
- **`surfaces.<harness>` narrows a harness to categories.** Categories are `instructions`, `rules`, `skills`, `agents`, `commands`, `hooks`, `mcp`, `settings`; an unnamed harness gets all of them. Projection empties the other categories in that harness's model, so no second code path exists: outputs a harness stops getting retire like a removed harness's outputs. Naming an unlisted harness is a validation error. The shared skills directory follows the union of harnesses that read it and get `skills`, so it cannot be withheld from one of them.

### 6. Backups and restore

- **Takeover snapshot.** Before Canonfig first writes any owned surface of a harness, it copies every owned file and directory into `~/.canonfig/.backups/<UTC timestamp>/<harness>/...` and writes `~/.canonfig/.backups/<UTC timestamp>/manifest.json` (harness, resolved root, path, object kind, mode, symlink text, SHA-256, `absent` markers, run id). For key-owned files the snapshot stores only the owned keys' prior values in `keys.json`, never the whole file, so `~/.claude.json` OAuth data never enters a backup. Directories are mode 0700, files 0600, Windows ACLs through the existing protected writer.
- **Retention.** Keep the first harness snapshot (the state before Canonfig ever wrote to a harness), the first folder snapshot (below), plus the 4 most recent; prune the oldest of the recent ones after writing a new one. The two firsts are kept apart so a folder snapshot taken before any takeover never pushes out the first harness snapshot. Delete a failed run's snapshot only after rollback completes. If rollback fails, retain the affected takeover entries and original content for `canonfig restore`; discard only entries whose rollback completed or whose writes never started.
- **Later applies** use the existing per-run journal and rollback material under the cache directory (`docs/file-rollback.md`). Snapshots are not taken per run.
- **`canonfig restore [<snapshot>]`** (default: latest) runs as a journaled Synchronization Run: it writes the snapshot back, removes Canonfig-owned entries the snapshot marks absent, deletes the Applied Resource Records for those surfaces, and adds the harness to the local exclusion list so the next sync does not take it over again. Config keys a later run took over in the same file are not in the snapshot: they stay written and owned. It refuses a harness whose owned surfaces have drifted since Canonfig's last apply.
- **Folder snapshots.** `canonfig import --replace` first snapshots the Canonical Folder entries it replaces, in the same layout and manifest with owner `canonfig` in place of a harness (copies under `canonfig/.canonfig/...`), under the import run's id, so rollback deletes it like a takeover snapshot. Restoring one writes those entries back with no drift check, since Canonfig never owns authored content and has no applied state to compare, after snapshotting what they hold now, so the restore is itself undone by `canonfig restore`. It excludes no harness, and an enrolled Follower refuses it: its folder is the Source's mirror.
- **Restore requires current ownership of every captured config key.** A remaining file-level record does not authorize rewriting keys that an earlier restore released.
- **Local exclusion pauses projection, not ownership.** Existing owned surfaces remain untouched and restorable across subsequent syncs, including surfaces captured by a different snapshot from the one just restored. Removing a harness from the Source list still retires its outputs unless that machine locally excludes it.
- **Restoring shared skills excludes their consumers.** A shared-skills-only snapshot excludes the selected harnesses that use `~/.agents/skills/`, so the next sync cannot immediately replace the restored directory.
- **Off switch.** `--no-backup` on `sync --apply`, or `"backups": false` in `local/local.jsonc`. The setting is machine-local on purpose: a Source cannot turn off a follower's safety net. The plan states `no backup` for every takeover it performs without one.

### 7. `canonfig.jsonc`

```jsonc
{
  "version": 1,
  "profile": { "id": "workstation", "name": "Workstation" },
  "harnesses": ["claude-code", "codex", "opencode"],
  "mcp": {
    "docs": { "transport": "streamable-http", "url": "https://example.invalid/mcp",
              "headers": { "Authorization": { "fromEnv": "DOCS_MCP_TOKEN" } } },
    "git": { "transport": "stdio", "command": "uvx", "args": ["mcp-server-git"], "requires": ["tools/uv"] }
  },
  "hooks": [{ "id": "format", "event": "after_tool", "matcher": { "capabilities": ["write"] },
              "run": ["hooks/format.sh"], "timeoutMs": 5000, "onFailure": "warn" }],
  "settings": { "codex": { "model_reasoning_effort": "high" }, "claude-code": { "model": "opus" } },
  "tools": { "uv": { "upstream": "https://github.com/astral-sh/uv", "recipes": { /* today's tool spec */ } } },
  "credentials": { "docs-token": { "reference": "DOCS_MCP_TOKEN" } },
  "groups": { "work": ["mcp/docs", "skills/deploy"] },
  "scheduleDefault": "daily@09:00",
  "local": { "allow": ["instructions", "skills", "mcp", "settings"], "appendLocal": ["instructions", "skills"] },
  "resources": { "gitconfig": { "kind": "file", "target": "~/.gitconfig", "source": "files/gitconfig" } }
}
```

`groups` lists items visible only to followers in that group; unlisted items go to every follower, the same semantics as today's grouped and ungrouped resources (`src/enrollment/enrollment.layer.ts:104-152`). `requires` becomes a resource dependency. `settings.<harness>` keys are merged into that harness's settings file; adapters reject keys on their never-touch list, and values pass the existing publication credential checks (`src/profile/publication-credentials.ts`).

### 8. Tools, installers and local overlays

- **Tools** keep today's spec: platform recipes, exact versions, `buildPolicy`, `verify`, `login`, `agentInstall`. They compile to the existing `tool` resource and run through the existing planner, executor and Configuration Agent policy. `canonfig source scan` scans the Canonical Folder (instructions, skills, hook scripts, MCP commands) instead of `--file` lists and proposes `tools` entries for review. Installer bindings stay machine-local in `~/.canonfig/installers/`.
- **Authored resources are bounded, not arbitrary.** `resources.<id>` in `canonfig.jsonc` (section 11) authors a file, directory or config file under the home directory, outside every harness. Harness surfaces stay the adapters' alone.
- **Local items** live in `~/.canonfig/local/`: the same layout plus `AGENTS.md` and `local.jsonc` (MCP servers, settings, harness and resource exclusions, overlays, `backups`). It is never published and never replaced. Projection adds local items to published ones within `local.allow`; a name that collides with a published item is Human Action Required unless a Local Overlay (section 11) names it. Keys a harness file holds outside Canonfig's owned set are follower-owned without any declaration.

### 9. Security

- Ownership is a positive allowlist per adapter; nothing outside an owned surface is written, read into a plan, or backed up. Tests assert, per adapter, that no planned target or snapshot path equals or contains a never-touch path.
- Every target is resolved under the pinned root with the existing no-follow, lexical and realpath checks; symlinked components are refused for writes.
- Publication reads only the authoring allowlist, enforces the existing realpath-inside-source rule, keeps MCP secrets as `fromEnv` references, and rejects credential-looking literals.
- Hooks and MCP stdio commands run code on followers; the plan lists every command before apply, as project hooks do today.
- Snapshots and journals are local, private and never transferred. Takeover, restore and every run stay in the SQLite journal.

### 11. Machine-owned content: append-local, Local Overlays, authored resources

The motivating case: Source A publishes skills, rules and `AGENTS.md`. Follower B has its own skills and its own instructions. B must get A's items and keep its own while Canonfig projects both into B's Codex (`~/.codex/AGENTS.md`, shared `~/.agents/skills/`). Three mechanisms cover it, all on the one planner, executor, journal and recovery path.

**Local instructions.** `instructions` joins `local.allow`. With it, `~/.canonfig/local/AGENTS.md` is appended after the published `AGENTS.md` in every harness's instructions, inside Canonfig's section. This is the folder-native way to add text to all of B's harnesses at once.

**`append-local` (Source-declared, `local.appendLocal`).** `canonfig.jsonc` `local.appendLocal` names harness categories whose outputs Canonfig shares with each machine: `instructions` and `skills`. It travels with `local.allow` in the `local-policy` item, so the Source decides for every follower, as v5.0.1's per-resource `policy` did. Authored `file` and `directory` resources take the same policy (`"policy": "append-local"`).

- *Text files* keep the v5.0.1 format: `<!-- canonfig:source:start -->`, the Source text, `<!-- canonfig:source:end -->`, a blank line, then the machine's text. The Applied Resource Record and verification hold the digest of the Source text only. Drift is the three-way rule on that section; the machine's text is never drift. First adoption keeps the whole existing file as the machine's text, even when it equals the Source text, because matching bytes do not prove ownership. The plan says so and names `canonfig sync --plan --review-local`. A file Canonfig owned whole under another policy converts without keeping its old copy as local text when it is unchanged, and is Follower Drift when it was edited. Removal (and `restore`) takes out only the Source section; when no machine text follows it, the file goes too, so a file Canonfig created does not stay behind empty (a zero-byte file the machine had before adoption goes the same way). Source text must be UTF-8 without NUL or the reserved markers; publication and projection refuse it otherwise.
- *Text transition intent.* Every file-write action records one intent: whole-file write, new Source section, first unmanaged adoption with retained digest, whole-file conversion with its applied digest, section update with its previous Source digest, matching orphan-section adoption, or leaving a section with no local suffix. `classifyTextOwnership`, `planTextWriteTransition` and `checkTextWriteTransition` in `src/domain/synchronization.ts` own this distinction; planning, execution and review do not infer it from optional digest fields. Markers without an Applied Resource Record are explicit orphan evidence: a matching Source section can establish ownership, a differing section is drift, and its local suffix is preserved. Execution rechecks the intended transition against its rollback preimage, including local text added after a plan to turn sharing off.
- *Directories* are new: Canonfig owns the top-level entries it writes (one skill directory, one file) and everything beneath them. Every other top-level entry belongs to the machine: not compared, not drift, not removed. A machine's file added inside one of Canonfig's entries is drift, as in any owned tree. An entry the machine holds under a name Canonfig would write but that the Applied Resource Record does not own (every name on first adoption, a newly published name later) is Follower Drift (rename one), even when its bytes equal the published ones: recording the machine's copy as Canonfig's would let a later retirement or restore delete it. This mirrors the `local/` name-collision rule and is how B's own skills in `~/.agents/skills/` survive.
- *Review.* `sync --plan --review-local` writes one private JSON per first text adoption (`sourceAddition`, `retainedLocal`, `proposedText`, digests, revision, plan digest) under `~/.canonfig/.reviews/adoption-review-<uuid>/` (directory 0700, files 0600). The text never enters the plan, the journal or the command output. It works on the Source, unenrolled machines and followers, and only with an interactive `--plan`.
- *Restore.* A takeover snapshot is still taken. `restore` of an append-local surface does not write the snapshot back over the machine's later edits: it retires Canonfig's section or entries, which leaves exactly the machine's content (first adoption kept all of it).
- *Turning it off* switches the surface back to whole-file ownership. A text file whose Source section is unchanged and holds nothing after the closing marker is rewritten as the plain payload, which drops the markers. Text after the marker stops the run with Human Action Required and the file unchanged; an edited Source section is Follower Drift. A directory reports Follower Drift wherever the machine's entries remain. The person moves that content (for example into `local/AGENTS.md`) and syncs again. Canonfig does not guess.

**Local Overlays (machine-declared, `local/local.jsonc` `overlays`).** An overlay is a machine's explicit decision that its `local/` item replaces the published item of the same name, instead of the name collision stopping the run. Items are `rules/<id>`, `skills/<name>`, `agents/<id>`, `commands/<id>`, `mcp/<name>` and `settings/<harness>` (local keys replace the published keys they overlap; other published keys stay). `canonfig overlay list|set|remove` edits and reports them (`set` and `remove`, like `harnesses include|exclude` and restore's exclusions, rewrite `local.jsonc` under the run lock, so two edits or an edit and a restore cannot lose each other's change); `list` says whether each finds a local item and a published one, and the plan warns about an overlay with no local item. The Source's `local.allow` still gates the category, overlays are never published or mirrored, and a new revision does not touch them.

**Key claims (machine-declared, same `overlays` list).** A key claim, `settings/<harness>#<key path>` (for example `settings/codex#model`), is a machine's decision that one key in that harness's settings file is its own: Canonfig never writes, removes or reports drift on it there, and every other key it owns in the file still comes from the Source. Where an item overlay swaps in the machine's value through `local/`, a claim lets the machine edit the harness file itself. The shape follows the planner: config surfaces are owned key by key, takeover already names a single key `<surface>#<key>`, and the settings file is the one config surface the folder authors keys into, so a claim is exactly one owned key path given back. `canonfig overlay set|remove` takes the same entry; nothing else needs a second command or list.

- *Valid claims.* The harness must be known and have a settings file Canonfig writes (Hermes has none), the key path must parse, and it must not overlap a key the harness keeps for itself (`provider`, `model.*.api_key`), which Canonfig never writes anyway. `overlay set` checks all of this before it records the claim; a hand-edited claim fails the next plan or sync the same way, before anything is written. A claim inside a key Canonfig writes as one value (`settings/codex#mcp_servers.docs` under `mcp_servers`) is refused by the sync that would need it: honoring it would mean owning part of a value. A local setting for a claimed key is refused too, since it asks Canonfig to write the key the machine took. A claim that covers no key Canonfig writes in that file changes nothing and the plan warns about it.
- *Projection.* Claimed keys leave the settings file's content before takeover is counted, so a claimed key is never taken over or snapshotted later. A key the Applied Resource Record still owns under a claim is given back untouched (`releases` outside the written `keys`): not removed, not compared. When a claim covers every key of the file, or the file stops being projected in the same run, Canonfig plans the file with no keys so that retirement cannot remove the claimed one; the next run retires the empty record without touching the file.
- *Drift.* The record holds one digest over all its keys, so the sync that first gives a key back cannot check the other keys on their own if the machine already edited the claimed one. It accepts the file when the other keys already hold the published values and nothing is removed; otherwise (the same revision also changes one of them) it reports Follower Drift, as it would for any edit it cannot attribute. After that sync, the record names only the kept keys and the normal three-way rule applies to them.
- *Removal.* Removing a claim hands the key back to the Source: the next sync writes the published value over the machine's, and drift protection covers the key again from then on. A takeover snapshot taken before the claim still holds the key's original value; `restore` refuses a snapshot whose captured keys Canonfig no longer owns, a claimed key included, until the claim is removed and a sync converges.
- Claims are machine-local, never published or mirrored, and are not gated by `local.allow`: they keep a key out of Canonfig's hands instead of adding one. Authored `resources` are the Source's alone; their keys cannot be claimed.

**Authored resources (`resources.<id>` plus `files/`).** `kind` is `file` (`source` under `files/`, `policy` `replace` or `append-local`), `directory` (`source` directory under `files/`, same policies) or `config` (`format` json, toml or yaml, `keys` as `settings` keys, always merged on owned keys). They publish as a `resources:<id>` JSON item plus one file item per file under `files/` (every file must be read by a resource), mirror like every other item, honor Follower Groups through `resources/<id>` (a file follows the resources reading it), and are untouched by `surfaces`, which selects harness categories. Projection makes each one a surface of the pseudo-harness `resources` rooted at the home directory (resource id `harness:resources:<id>`), so takeover snapshots, root pinning, three-way drift, removal and `restore` work unchanged; a restored resource goes into `local.jsonc` `excludeResources`, the counterpart of `excludeHarnesses`. Targets are written `~/...` with no `.` or `..` segment, must not overlap each other, and must not overlap the Canonical Folder, `~/.agents/`, or any adapter's root, surface target or never-touch path, whether or not that harness is listed. Overlap is compared without case in the folder (it reaches case-insensitive file systems) and again on each machine with that platform's rules. The bound is checked on the resolved path too: every existing ancestor below home must be a real directory (no symlink or junction) and the ancestry must resolve inside home, before the target is read, snapshotted or taken over, again right before each executor preparation, mutation and rollback, and before recovery restores a rollback snapshot. It is a check, not an anchored write: a parent replaced by a link between the check and the path-based write after it is still followed. `MachineState.mutateWithinRoot` would close that window, but its macOS strategy renames its root aside while it works, and here the root would be the home directory. That bound replaces v5.0.1's unbounded targets: a resource cannot reach `~/.codex/auth.json`, directly or through a link. Moving a resource to a new target needs a new id, so the old target retires through the normal path.

### 12. Export and import

`canonfig export [--output <file.tar.gz>] [--include-harnesses] [--force]` writes the folder to one archive; `canonfig import <file> [--dry-run] [--replace] [--expect-key <fingerprint>]` brings it back.

- **Contents are an allowlist, read once.** `manifest.json` first, `signature.json` next on a Source, then `folder/` holding the authoring allowlist plus `local/`; nothing else in `~/.canonfig/` is opened. The loader's listing refuses links and paths resolving outside the folder, then each file is read exactly once through `MachineState.readFile` anchored at the real folder (no link anywhere below it: descriptor-relative on Linux; on macOS and Windows a before-and-after identity walk around a pathname read, which detects a parent still swapped afterwards but not one swapped for a link and put back between the two walks), non-blocking so a FIFO is refused, and bounded by what remains of the 128 MiB content budget, checked on the opened file before reading and while reading. Those exact bytes are the ones checked and archived: every folder file, comments and hook scripts included, gets the literal-credential pattern check, and the `mcp`, `hooks` and `settings` items decoded from those bytes of `canonfig.jsonc` and `local/local.jsonc` also get publication's field-name rule; credential file names (`.env*`, `auth.json`, `credentials.json`) refuse the export. `--include-harnesses` adds `harnesses/<harness>/<path below home>` from the Applied Resource Records, read the same way anchored at the real home, only for surfaces whose content still equals what Canonfig last wrote, and for a directory only while it holds no entry Canonfig did not write (others are reported and left out); a key-owned file contributes its owned keys rendered alone, never the whole file. Authored resources come under `harnesses/resources/`; an `append-local` surface is always left out, since it also holds the machine's own content (section 11). Harness files are not pattern-scanned: they are projections of the checked items, and harness syntax such as Codex's `env_http_headers` (a header mapped to a bare variable name) reads as a literal to the pattern.
- **Manifest.** Canonfig version, creation time, role (`source`, `follower`, `standalone`) and per file path, size, SHA-256 and octal mode; harness entries add `harness`, `target` and `keys`. Entries sort by path, tar headers carry owner, group and time 0, so equal input and time give equal bytes (Ed25519 signatures are deterministic, so a signed export too). On its own it is an integrity record; export also prints the archive digest for out-of-band comparison.
- **Signing.** On a Source, export signs `canonfig-export-manifest:<manifest SHA-256>` with the Source signing key through the same signer that signs Profile Revisions (the prefix keeps the payload from ever reading as a revision's canonical JSON), and writes `signature.json` (`fingerprint`, SPKI PEM `publicKey`, `ed25519:` signature) right after the manifest; the manifest cannot list it, since it signs the manifest. A Source whose key cannot be loaded or does not match its identity exports nothing rather than an unsigned archive. Other roles export unsigned. Import verifies a present signature before anything else (the key must hash to the named fingerprint and the signature must hold) and refuses the archive otherwise; it reports the fingerprint or `unsigned`. The key travels in the archive, so a valid signature only names a key: `--expect-key <fingerprint>` (the `sourceFingerprint` that `status` shows on the Source) refuses an unsigned archive or another key's, which also covers a stripped `signature.json`.
- **Output.** A `.tar.gz` in an existing directory inside home and outside `~/.canonfig/`, checked early for a clear message and enforced again at publication: `atomicWrite` with `anchor` set to the real home publishes only into that directory reached without links, and without `--force` uses `noReplace`, a hard-link publication that refuses an existing file even when it appeared after the checks (a filesystem without hard links needs `--force`). On macOS and Windows that anchoring is the weaker walk described above. A failure after the archive became visible (the identity check, the directory flush, Windows permission finalization) comes back from the layer as `UnconfirmedPublicationError` and from export as `ArchivePublicationError`, which says whether the path holds the complete archive or no longer names it, and with `--force` that the earlier archive was already replaced; export never removes the destination on that path, since a check followed by a removal could delete another writer's file. Mode 0600 (ACL on Windows); a hook script's mode follows the Windows executable-intent rule below. Format and limits follow the deleted archive code: PAX paths, gzip, 20,000 files, 128 MiB of content, portable path rules, case collisions refused. ZIP is dropped. Import reads the archive with one no-follow, non-blocking, size-bounded read.
- **Import verifies, then runs.** The archive must list every entry exactly once with matching size, digest and mode, hold only regular files inside the allowlist (or `harnesses/<harness>/` entries the manifest names), carry nothing but zero padding after the end-of-archive marker, and contain a decodable `canonfig.jsonc` and, when present, a decodable `local/local.jsonc`; links, devices, directories, absolute or `..` paths and unknown PAX fields refuse the whole archive. The folder entries are then written as one Synchronization Run (`origin: "archive"`, `originDigest` the manifest digest) through the shared planner, executor, journal, rollback and recovery. Each entry is a `replace` resource whose ownership ends in the same run, like restore, so a later sync never retires imported content. Without `--replace` the planner marks every `write-file` action `noReplace`, so a file created at a target after the occupancy check fails that write with EEXIST instead of being replaced; the write's rollback leaves the file alone (a target that was absent is removed only while the name still refers to the file the write published, judged from `atomicWrite`'s returned identity), and import reports `ArchiveConflictError`. Directory entries go through `mirror-directory`, which has no such guard.
- **Refusals.** An enrolled Follower is refused before the archive is read: its folder is the Source's mirror. A folder holding any authored entry, or `local/` when the archive has one, is refused unless `--replace`; `--replace` replaces exactly the entries the archive holds, after a folder snapshot of them (section 6), and keeps (and reports) the others, so nothing the archive does not speak for is deleted.
- **Harness files are never imported.** They are verified and counted. The next `canonfig sync` projects the imported folder through takeover, with its snapshot, which is the only path that may write a harness surface.
- **Export is not a Synchronization Run.** It changes nothing Canonfig manages, and recording a converged run would replace the outcome `status` reports for the last real sync. Export and import (all but `--dry-run`, which writes nothing) are journaled instead in `archive_events`, a state table of their own added by migration `0002_archive_events` and kept append-only by triggers: time, command, outcome (`Exported`, the import run's outcome, or `Error`), archive path, SHA-256 and signer. Status and diagnostics list no recent activity, so the table is read directly. The command journal (`canonfig.log`) also records both, and the run journal records every import's run.

## Consequences

- Users author one folder in the shapes harnesses already use; Canonfig owns paths, formats and translation.
- Taking over a harness removes configuration the user had there. The snapshot and `restore` make that reversible, and drift rules keep later local edits.
- Adapter correctness now affects global setup on every follower, so adapters need golden fixtures for all three OSes and a per-release documentation re-check.
- Followers keep their own content beside published items where the Source allows it (`local/`, `local.appendLocal`), may replace a published item on one machine with a Local Overlay, and may keep one settings key as their own with a key claim. Everything else they change is Follower Drift or a question for the Source.

## Rejected

- **Keep the JSONC Machine Profile and add harness resources to it.** Authors keep writing native paths and formats by hand, and arbitrary targets stay possible.
- **Folder next to the profile** (`~/.canonfig/` projected locally, `profile.jsonc` still published). Two sources of truth, two engines, and followers never get the folder.
- **Whole-folder replace of each harness home.** Auth, sessions and history share those directories and files (`~/.claude.json`, Devin's Windows root, `agent.db`), and a denylist cannot keep up with vendors adding state files.
- **Symlink harness surfaces into `~/.canonfig/`.** Windows symlinks need privileges, several harnesses mix state into config files, and drift would be invisible.
- **Project per harness on the Source and publish native files.** Roots depend on each follower's OS, environment and installed harnesses.

### Direct hook execution on Windows

A Windows Source cannot observe POSIX executable bits. When an enabled hook directly names a script under `hooks/`, publication treats that explicit command as executable intent for followers. A script referenced only by disabled hooks retains its observed mode. Unix Sources continue to publish their actual mode. `canonfig export` applies the same rule (`intendedExecutable` in `folder.ts`) to the mode it archives. This preserves execute permission, not interpreter availability or shell compatibility across operating systems.
