---
title: Tool discovery and Installation Recipes
description: Author evidence-backed, pinned, platform-specific tool recipes with independent verification.
---

A tool Profile Resource uses the `ensure` Apply Policy. Canonfig first selects a
deterministic **Installation Recipe** for the follower platform. Only ambiguous
work can become an Agent Task.

Tools are the only resources discovery proposes. File, directory, config, and
skill resources are always authored in the profile file; see the
[profile reference](/reference/profile-schema#author-file-config-and-skill-resources).

## Discovery evidence

`canonfig source scan --file <path>` reads only the files you name. It runs no
processes: it never starts a package manager, a shim, or a discovered tool.
It can find tool evidence in:

- executable shell blocks in agent instruction Markdown;
- hooks and MCP configuration;
- JSON, JSONC, TOML, shell, Brewfile, winget, and package metadata;
- resolved executables on `PATH`;
- explicit `canonfig.tools` package metadata.

Each accepted tool needs an upstream URL and at least one verification method.
Evidence that is not enough to decide becomes `needs-review` with a task that
says why:

- Inline Markdown prose is never treated as an install command.
- A `canonfig.tools` entry missing its ecosystem or name is kept with the
  missing fields listed (`incomplete-declaration`).
- Several distinct copies of the same executable on `PATH` are listed with
  their path, version, modification time, and digest (`ambiguous-executable`).

`uvx <package>`, `uvx --from <package> <command>`, and `uv tool install` or
`uv tool run` invocations with a pinned package (`==` or `@`) become uv recipes.
MCP servers get `executable-present` verification, so checking one never
launches the server.

## Recipe shape

A tool resource can carry independent platform recipes:

```jsonc
{
  "id": "ripgrep",
  "kind": "tool",
  "target": "rg",
  "spec": {
    "kind": "tool",
    "toolId": "ripgrep",
    "recipes": [
      { "platform": "linux", "method": "apt", "package": "ripgrep", "version": "14.1.0-1" },
      { "platform": "macos", "method": "brew", "package": "ripgrep", "version": "14.1.1" },
      { "platform": "windows", "method": "winget", "package": "BurntSushi.ripgrep.MSVC", "version": "14.1.1" }
    ],
    "login": { "required": false }
  },
  "verify": {
    "method": "command",
    "command": ["rg", "--version"],
    "expectContains": "ripgrep 14.1"
  }
}
```

The package name and installation method are platform facts, not portable
aliases. Do not infer a Windows package ID from an npm package name or copy a
Homebrew formula into a Linux recipe.

Every automatic recipe (npm, pnpm, bun, brew, apt, winget, uv, cargo) needs an
exact `version`. Publication refuses one without it, for example "installer uv
requires an exact \"version\" so every follower installs the same build", so
the mistake surfaces on the Source Machine rather than on each follower.

## Installed tool observation

For command verification, `target` identifies the installed tool: a command
name or a path to its entry file. Planning checks that target, not the first
word of the verification command, which may be a shared runtime such as Node or
Python. An `executable-present` verifier instead names the executable to check
explicitly. `toolId` remains the portable resource identity.

Planning does not run verification commands. Presence allows `ensure` to leave
an existing installation in place; the declared verification still checks it
during apply. A present entry file alone does not prove the expected version,
working dependencies, or a signed-in session.

## Verification lookup

A bare command name in a verifier, such as `ruff`, is resolved in this order:

1. the directories where this tool's recipes install executables on this
   platform: for uv `$XDG_BIN_HOME`, then `$XDG_DATA_HOME/../bin`; for npm its
   prefix `bin` and the Node directory, plus `%APPDATA%\npm` on Windows; for
   pnpm `$PNPM_HOME`; for bun `~/.bun/bin`; for cargo `~/.cargo/bin`; for brew
   the Homebrew prefix `bin`; for winget
   `%LOCALAPPDATA%\Microsoft\WinGet\Links`;
2. `~/.local/bin`, always;
3. `PATH`. In a scheduled run that is the bounded `PATH` of the native job.

apt installs into system directories that every `PATH` already contains. So a
tool that uv just installed into `~/.local/bin` verifies even when the shell
`PATH` or the scheduler's `PATH` does not include that directory. When the
executable is not found anywhere, verification fails and names every directory
it searched: "verification failed for resource `<id>`: verification executable
ruff was not found (searched: …)".

## Setup execution

`canonfig setup plan --role <source|follower> --file <path>` feeds bounded
declared files through this discovery pipeline. Accepted recipes become
per-resource plan items only when their native installer is present. The plan
stores the installer executable, argument vector, independent verifier,
version, source, upstream, and integrity metadata; it never stores shell text.

Planning has no side effects. Installer version probes run with
`COREPACK_ENABLE_NETWORK=0`, `COREPACK_ENABLE_AUTO_PIN=0`,
`COREPACK_ENABLE_DOWNLOAD_PROMPT=0`, and `RUSTUP_AUTO_INSTALL=0`, so a Corepack
or rustup shim cannot download a toolchain or pin a version. A rustup proxy
such as `cargo` is not run until rustup has a `settings.toml`; the tool is then
reported unverified, and apply fails that optional item with "run `rustup
default stable`". A fresh home directory stays untouched by `setup plan`.

After `setup approve`, `setup apply` executes those known recipes directly and
records verification evidence and provenance in the setup journal. An
unavailable or failed optional recipe does not block unrelated required work.
Unknown or ambiguous recipes remain exclusions for review; setup does not
delegate them to an outer agent.

## Supported discovery methods

Discovery can resolve deterministic metadata for npm, Homebrew, winget, uv,
cargo, and source recipes when evidence is sufficient. A source recipe must
include its upstream repository and bounded build commands.

## uv recipes

For uv recipes, `indexPolicy` may explicitly review a full credential-free
HTTPS simple-index URL with `reviewedBy` and `reviewedAt`. Private simple-index
subpaths remain intact. Without that policy, Canonfig uses the fixed
`https://pypi.org/simple` index. Deterministic uv actions use `--no-config`,
the full approved `--default-index`, exact package versions, and
`uv tool install --no-build` under the default build policy. `--only-binary`
belongs to the pip interface and is not a valid `uv tool install` option.

uv never downloads a Python interpreter for Canonfig. Every uv install runs
with `--no-python-downloads` and `UV_PYTHON_DOWNLOADS=never`, set after the
inherited `UV_` variables are cleared, so an inherited setting cannot turn
downloads back on. A package that needs a Python the machine does not have
fails with uv's own message.

## npm configuration isolation

Automatic npm-family installs ignore inherited package-manager configuration.
Canonfig resets separate user and global npm config files to empty content in
its cache before each install. The two paths must differ because npm rejects
loading one path at both configuration levels. These files contain no credentials
and are reusable cache material, not user settings.

## Installer failures

When an installer exits with an error, the failure includes the end of what it
printed: "installer `<method>` exited with `<code>`; its last output lines:"
followed by at most 20 non-empty lines of standard error (or standard output
when standard error is empty), capped at 1536 characters and redacted. An
installer that printed nothing is reported as having printed no diagnostic.
Tool installs are outside the run's rollback: a package already installed stays
installed. See [the transaction boundary](/explanation/architecture#the-transaction-boundary).

On Windows, `.cmd` and `.bat` shims such as `npm.cmd` cannot run without a
shell; bind the package manager to its JavaScript entry point instead (see
[Windows package managers](/reference/cross-platform#windows-package-managers)).

## Login requirements

A recipe may declare that login is required and provide non-secret instructions.
Login is never considered deterministic proof and credentials are never copied
from the Source Machine. If no usable local credential exists, synchronization
records Human Action Required.

<Callout title="Never put credentials in a recipe" type="error">
  Recipe arguments, environment examples, verification output, and profile
  content must not contain tokens, passwords, private keys, cookies, or complete
  invitation payloads. Use a credential reference and local secure storage.
</Callout>

## Ambiguous recipes

When evidence cannot select one safe recipe, discovery creates a bounded Agent
Task with the upstream URL and evidence. A Configuration Agent may propose a
recipe, but it cannot publish that proposal. Under agent apply, the controlled
executor still enforces the task bounds and runs verification afterward.
