title: Platform differences
description: Look up how Canonfig differs on Linux, macOS, and Windows in harness roots, backups, tools, credentials, schedules, and unattended runs.
---

Linux, macOS, and Windows can each run a Source Machine or a Follower Machine.
The Canonical Folder means the same thing on each platform. Each Follower
Machine resolves harness roots, package managers, credential stores, and
schedulers for its own platform, so you never publish a platform's paths.

## What Canonfig uses on each platform

| Capability | Linux | macOS | Windows |
| --- | --- | --- | --- |
| Follower Machine schedule | systemd user timer | launchd user agent | Task Scheduler task |
| Source Machine service | systemd user unit `canonfig-source.service` | LaunchAgent `dev.canonfig.source` | Task Scheduler task `Canonfig\canonfig-source`, started at logon |
| Credential store | Secret Service (for example GNOME Keyring) | login Keychain | Credential Manager |
| Typical installers | apt, npm, uv, cargo, source | Homebrew, npm, uv, cargo, source | winget, npm, uv, cargo, source |
| Path syntax | POSIX | POSIX | Windows |

## Harness roots

`~/.canonfig/` is in your home directory on every platform: `$HOME` on Linux
and macOS, `%USERPROFILE%` on Windows. Each machine resolves every harness root
itself, from its own environment and platform:

| Harness | Linux and macOS | Windows |
| --- | --- | --- |
| `devin` | `~/.config/devin` | `%APPDATA%\devin` (with `credentials.toml`, which Canonfig never touches) |
| `copilot-cli` | `$COPILOT_HOME`, else `~/.copilot` | `%COPILOT_HOME%`, else `%USERPROFILE%\.copilot` |
| `amp` | `~/.config/amp` | `%USERPROFILE%\.config\amp` |
| `opencode`, `kilo` | `$XDG_CONFIG_HOME/<name>`, else `~/.config/<name>` | the same, under `%USERPROFILE%\.config` |
| `cursor` | `~/.cursor`; on Linux, `cli-config.json` follows `$XDG_CONFIG_HOME/cursor` | `%USERPROFILE%\.cursor` |
| every other harness | its override, else a directory under `~` | the same under `%USERPROFILE%` |

The full list is in the [harness reference](/reference/harnesses). Every root
must resolve inside your home directory, and Canonfig pins the root it used at
takeover; a later run that resolves another root stops with Human Action
Required instead of writing a second copy.

Agent harness allowlists (`canonfig agent harness --allow-path`) belong to each
Follower Machine. Use Windows paths on Windows and POSIX paths on Linux and
macOS.

## Takeover snapshots

Snapshots under `~/.canonfig/.backups/` are private on every platform. On
Linux and macOS, directories have mode `0700` and files `0600`. On Windows,
Canonfig sets an ACL that grants only your user, through the same protected
writer it uses for every file. A snapshot stores paths relative to your home
directory, so it belongs to the machine that took it.

## File writes

Canonfig writes each file to a temporary sibling named `.cf-<12 hex>.tmp`,
then renames it over the target, so a target is never left half written.
`canonfig recover` removes leftover temporary files.

### Windows path length and symbolic links

Unless Windows long paths are enabled, Windows limits paths to 260 characters
(MAX_PATH). `canonfig sync --plan` and `canonfig sync --apply` measure each
target, including the temporary name, and refuse a target that is too long
before they change anything:

> `<path>` needs N characters including Canonfig's staging names, but this
> machine accepts file paths of at most 260 characters because Windows long
> paths are not enabled (MAX_PATH is 260). Nothing was changed.

To fix it, shorten the item that makes the path long, such as a file deep in a
skill directory, or enable long paths from an administrator PowerShell and
open another session:

```powershell
Set-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem' -Name LongPathsEnabled -Value 1
```

If an apply fails after it created parent directories, rollback and
`canonfig recover` remove the directories that run created, and only while
they are empty. Directories that existed before the run stay.

Creating a symbolic link on Windows, for example when `canonfig restore`
writes back a link the snapshot recorded, needs Developer Mode or the "Create
symbolic links" user right. Without either, the action fails with:

> Windows refused to create a symbolic link (EPERM). Creating symbolic links
> requires Developer Mode (Settings > System > For developers) or the
> SeCreateSymbolicLinkPrivilege user right ("Create symbolic links"); enable
> one for this account, sign in again, then retry

## Installation Recipes

Each platform has its own Installation Recipe. A tool can install with apt on
Linux, Homebrew on macOS, and winget on Windows. An npm, uv, cargo, or source
recipe covers several platforms only when it was verified on each of them.

To verify a bare command such as `ruff`, Canonfig looks first in the
directories where that recipe's installer puts executables, then on `PATH`.
On Windows these include `%APPDATA%\npm` and
`%LOCALAPPDATA%\Microsoft\WinGet\Links`. See
[How Canonfig installs and verifies tools](/explanation/tools-and-recipes).

## Windows package managers

Canonfig starts installers without a shell, and Windows `.cmd` shims such as
`npm.cmd` and `pnpm.cmd` cannot run that way. When `PATH` resolves npm to
`npm.cmd`, `canonfig sync --plan` shows a warning and `canonfig sync --apply`
stops with Human Action Required:

> No installer binding is set for npm, and PATH resolves it to the Windows
> command shim C:\Program Files\nodejs\npm.cmd, which cannot run without a
> shell. Bind npm to Node and its own entrypoint instead, then retry:

Run the binding command it prints, which looks like this, then check it:

```powershell
canonfig installer set npm --executable "C:\Program Files\nodejs\node.exe" --arg "C:\Program Files\nodejs\node_modules\npm\bin\npm-cli.js"
canonfig installer check npm
```

Both paths must be absolute and exist. They depend on where Node.js is
installed; nvm-windows and Volta use other directories. For pnpm, use
`pnpm.cjs` as the `--arg`. `canonfig installer list` shows the same command
under `suggestions`, and `canonfig installer check` confirms that the binding
starts. See [Installer bindings](/reference/cli#installer-bindings).

## Schedules

You declare a schedule once, in local time, and Canonfig installs the matching
native job:

```bash
canonfig schedule set daily@09:00 --timezone Europe/Paris
canonfig schedule status
```

`--timezone` works on Linux only. Missed runs and daylight-saving changes
follow each platform's scheduler; see [Sync on a schedule](/how-to/manage-schedules).

## Unattended runs

Every scheduled run executes:

```text
canonfig sync --apply --no-input --scheduled
```

A scheduled run never waits for a prompt. A missing credential store, login,
elevation, or other step only a person can take ends as Human Action Required.

A scheduled run starts with the native scheduler's environment, not your
shell's. Two things follow:

- **PATH.** The job's `PATH` is usually shorter, so it can detect fewer
  harnesses than your shell does. A harness it does not find stays as it was
  last applied; the run does not remove Canonfig's outputs there. Canonfig also
  searches its install directories and `~/.local/bin`, whatever `PATH` holds.
- **Pinned roots.** A root override such as `CODEX_HOME` or `CLAUDE_CONFIG_DIR`
  that only your shell sets is missing in the scheduled run, so the harness
  resolves to its default root. Because the root was pinned at takeover, the
  run stops with Human Action Required instead of writing a second copy. The
  message says what to do: give the run the environment the root came from,
  or run `canonfig restore`, then `canonfig harnesses include <harness>`, and
  sync again so Canonfig takes the harness over at the root the scheduled run
  sees.

The Source Machine's service and scheduled runs work under these conditions:

| Platform | While logged in | While logged out |
| --- | --- | --- |
| Linux | yes | only with lingering on (`loginctl enable-linger <user>`) and a reachable, unlocked Secret Service, or the local-file credential policy |
| macOS | in the logged-in desktop session, with the login Keychain unlocked | no |
| Windows | from logon, while you stay logged on | no |

See [Run Canonfig unattended](/how-to/run-unattended).

## Reaching the Source Machine

On every platform, the Source Machine listens on a loopback address only.
Canonfig does not support a public listener. A Follower Machine on another
host connects through the managed SSH tunnel, which pins the SSH host key, the
Source Machine's TLS certificate, and its signing key, and refuses options
that skip host-key checks or add forwards.

```bash
canonfig tunnel start --invitation ./canonfig-invite --ssh-host source.lan --ssh-user maria --ssh-host-key-file ./source-host-key.pub
canonfig tunnel start
```

The first command sets up and records the tunnel. Later starts need no
invitation, and a scheduled run restarts a tunnel that went down once before
it fetches. See the [CLI reference](/reference/cli#managed-ssh-tunnel).
