Canonfig requires Node.js 24 or newer. Commands render human-readable output by
default. Add the global `--json` option to receive a stable
`canonfig.cli/v1` envelope.

## Global options and environment

```text
canonfig --help
canonfig --version
```

`-h` and `-V` are the short forms. `--json` can appear anywhere in a
command.

Canonfig writes privacy-safe JSON Lines command lifecycle records to
`~/.canonfig/canonfig.log`. Use `CANONFIG_LOG=off` to disable them or
`CANONFIG_LOG_FILE` to select another path. Arguments and command output are
never recorded.

## Journaled machine setup

```text
canonfig setup plan --role source --file AGENTS.md --file package.json --intent "prepare source"
canonfig setup plan --role follower
canonfig setup approve --approver operator
canonfig setup apply
canonfig setup status
```

`setup plan` requires the machine role before any role-specific inspection.
It records a bounded OS, account, loopback transport, Node runtime, native
installer, and discovery inventory. A Source plan fails before initialization
when signing and TLS key storage is unavailable. Approval binds the plan
digest; apply runs only structured native argv recipes and journals evidence
and qualified provenance. Re-running apply resumes the next eligible stage.
An unavailable optional integration excludes only its dependent branch.

## Source Machine

```text
canonfig source init
canonfig source scan --file AGENTS.md --file package.json
canonfig source publish --proposal package.json --profile workstation --name Workstation --reviewer operator
canonfig source serve --host 127.0.0.1 --port 17342
canonfig source invite --endpoint https://127.0.0.1:17342 --output ./canonfig-invite --expires 15m --group developers
canonfig source revoke follower-one
```

`source serve` defaults to `127.0.0.1:17342`. `source invite` requires an
output path, writes a mode-`0600` bounded envelope with an explicit EOF marker,
and reports only its path and non-secret metadata. Invitation duration uses a
positive integer plus `ms`, `s`, `m`, or `h` and cannot exceed 24 hours. Repeat
`--group` to add Follower Groups.

## Follower enrollment and synchronization

```text
canonfig tunnel start --invitation ./canonfig-invite --ssh-host source.example --ssh-user operator --ssh-host-key-file ./source-host-key.pub
canonfig tunnel status
cat ./canonfig-invite | canonfig follower enroll --stdin --name laptop --profile workstation
canonfig tunnel stop
canonfig sync --plan
canonfig sync --apply
canonfig sync --apply --no-input
canonfig recover --no-input
canonfig abandon
canonfig status
canonfig status --follower follower-one
canonfig doctor --no-input --timeout-ms 5000
```

One machine holds one enrollment. Re-enrolling under the same name rotates the
credential and keeps the identity. Enrolling a different name needs
`--replace`, because the previous identity's Applied Resource Records are
addressed by an id that a new identity does not use.

The managed tunnel accepts only a verified SSH host public key and a loopback
forward. It rejects host-key bypass and extra-forwarding flags. Readiness
requires both the invitation's TLS fingerprint and Source signing fingerprint.
`tunnel status` reports SSH, TLS, and signing evidence separately; a stale PID
that does not match the recorded SSH command is never signaled.

`--plan` and `--apply` are mutually exclusive. With neither, `sync`
plans. A successful apply also synchronizes shared secrets when the follower has
the `canonfig:secrets` group. `recover` accepts only `--no-input`.

`recover` resumes an interrupted run, which needs that run's source revision to
still be authorized. `abandon` is the terminal close for a run `recover` cannot
resolve, such as one whose revision is gone or whose follower was pointed at
another profile. It is not a rollback: whatever the interrupted run already
applied stays applied, and the next run reconciles it like any other follower
state. Abandoning only stops the open run from blocking that.

`status --json` includes a `completionReceipt` after enrollment. It reports the
exact applied revision and separates signed publication, apply outcome,
explicit client-load evidence, native scheduling, and independent journal
verification. `secondRunNoOp` is true only when the latest converged run
performed no filesystem, configuration, removal, or tool-install mutation.
Scheduling remains `pending` until the native job is current and a real
`sync --apply --no-input --scheduled` invocation has completed.

## Shared secrets

```text
printf %s "$GITHUB_TOKEN" | canonfig secrets set github-token
canonfig secrets list
canonfig secrets sync
canonfig secrets remove github-token
canonfig secrets bootstrap
```

`secrets set` reads the value from standard input only. Secret values require
the native noninteractive credential store and are never accepted in argv,
printed, or written to JSON. `secrets sync` is an explicit retry; normal
successful `sync --apply` runs synchronize automatically.

On headless Linux, choose storage before bootstrapping. Secure storage is the
default:

```text
dbus-run-session -- canonfig secrets bootstrap
```

An intentionally unencrypted local file is an explicit operator choice:

```text
CANONFIG_LOCAL_CREDENTIAL_ROOT="$HOME/.canonfig/credentials" canonfig secrets bootstrap
```

The command runs as the current user and never invokes `sudo`. Install
`libsecret-tools` and a Secret Service provider such as `gnome-keyring` with
the distribution's package manager before running Canonfig when those packages
are absent. The secure path checks `secret-tool`, starts an installed
user-session provider when required, waits for D-Bus registration, and uses
disposable credentials to verify storage, lookup, and owned-provider restart.
Canonfig never replaces a provider it did not start. When logout or reboot
persistence cannot be proven without disrupting the current session, the
result says `manual` and asks for a restart followed by the same command.

The completion result names the selected `secure-store` or `local-file` policy.
It reports local-file backup storage as unencrypted and does not claim that a
provider collection is encrypted when the provider cannot attest it.

Bind a shared secret to an agent harness without writing its value into the
follower configuration:

```text
canonfig agent harness codex --executable /opt/codex --bind-secret MCP_TOKEN=shared-mcp-token
```

Canonfig persists only `MCP_TOKEN` and `shared-mcp-token`. It resolves the
current native-store reference immediately before spawning the harness, adds
the value only to that process environment, and includes it in output
redaction. Rotating the stored `shared-mcp-token` value therefore takes effect
on the next launch. MCP projections that use `{ "fromEnv": "MCP_TOKEN" }`
consume the same binding for environment-backed headers; unrelated secret
names are not loaded.

## Harness configuration

```text
canonfig harness init
canonfig harness init --format json
canonfig harness validate
canonfig harness targets
canonfig harness plan
canonfig harness apply
canonfig harness status
canonfig harness diff
canonfig harness clean
canonfig harness doctor
```

YAML is the default scaffold. `--format json` creates strict, pretty-printed
`.canonfig/harness.json` and is valid only with `harness init`. YAML and
JSON use the same schema and compiler. Canonfig rejects ambiguous projects that
contain multiple supported harness configuration files.

## Profiles and agent policy

```text
canonfig profile list
canonfig profile show revision-one
canonfig profile select workstation
canonfig agent policy
canonfig agent policy deterministic-only
canonfig agent policy agent-propose
canonfig agent policy agent-apply
canonfig agent harness
canonfig agent harness codex --executable /opt/codex --allow-path /home/operator/.canonfig --allow-leaf-executable npm --allow-origin https://registry.npmjs.org --allow-capability restart --maximum-input-bytes 4096
```

Harness kinds are `codex`, `claude`, and `gemini`. Capabilities are
`elevation`, `login`, `restart`, and `reboot`. Allow origins must be
exact HTTPS origins.

## Scheduling

```text
canonfig schedule set daily@00:00
canonfig schedule set weekly:Mon@12:30 --timezone Europe/Paris
canonfig schedule set daily@00:00 --executable /opt/canonfig
canonfig schedule status
canonfig schedule remove
```

The schedule CLI accepts daily and weekly calendars only.

## JSON envelope

```json
{
  "schema": "canonfig.cli/v1",
  "command": "status",
  "status": "success",
  "exitCode": 0,
  "message": "status completed",
  "data": {}
}
```

Secret-like fields are recursively redacted before human or JSON rendering.
Structured failures are written to standard error; structured successes are
written to standard output.

## Exit codes

| Code | Meaning |
| ---: | --- |
| `0` | Success |
| `1` | Internal failure |
| `2` | Usage or configuration |
| `3` | Human Action Required |
| `4` | Conflict or Follower Drift |
| `5` | Authentication or revocation |
| `6` | Transport |
| `7` | Verification or apply failure |

Code `1` is reserved for defects: an unexpected failure Canonfig has no
classification for. Every refusal Canonfig explains, including one it reports
under `--json`, carries one of the other codes, so a script can tell a
deliberate refusal from a crash.

Usage errors are reported in the requested output format. With `--json` they
arrive as a `canonfig.cli/v1` envelope with `status` `"error"` and `exitCode`
`2`, the same shape as every other failure.
