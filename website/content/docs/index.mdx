title: Canonfig

You keep one folder, `~/.canonfig/`, with your agent setup: instructions,
rules, skills, subagents, commands, MCP servers, hooks, settings, and the tools
they need. Canonfig writes that folder into the global configuration of every
harness you list, such as Claude Code, Codex, and OpenCode, translating it into
each harness's own files and formats. This is a **Projection**.

The machine where you edit the folder is the **Source Machine**. It publishes
the folder as a signed **Profile Revision**. Each **Follower Machine** checks
the signature, mirrors the folder into its own `~/.canonfig/`, and projects it
into the harnesses installed there. Follower Machines never send changes back.

Before Canonfig first writes to a harness, it copies what was there into a
**Takeover Snapshot** under `~/.canonfig/.backups/`, and `canonfig restore`
puts it back.

To see the commands and their output before you install anything, try the
[interactive demo](https://canonfig.micr.dev). It runs on simulated data.

## What Canonfig does not do

- It does not sync in both directions. A change made in a Follower Machine's
  mirror stays there as Follower Drift and never reaches the Source Machine.
- It does not touch a harness's logins, sessions, history, or trust decisions.
  In files a harness shares with its own state, such as `~/.claude.json`,
  Canonfig changes only the keys it owns.
- It does not publish arbitrary files. Only the folder's authoring entries
  reach Follower Machines.
- It does not run a hosted service. Your Source Machine serves the Profile
  Revisions.
- It does not guarantee that a third-party installer can be rolled back.

To learn which machine owns what and what one run can roll back, read
[How Canonfig works](/explanation/architecture).
