---
title: Sync your first two machines
description: Set up ~/.canonfig/ on one machine, project it into Claude Code and Codex there, and keep a second machine in sync with it every day.
---

At the end of this tutorial, machine A holds your agent setup in
`~/.canonfig/` and projects it into Claude Code and Codex, and machine B
receives the same setup and applies it on its own every day. Machine A becomes
the **Source Machine**. Machine B becomes a **Follower Machine**.

You sync:

| In `~/.canonfig/` on machine A | What Claude Code and Codex get on A and B |
| --- | --- |
| `AGENTS.md`, imported from `~/.claude/CLAUDE.md` | `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md` |
| the skill `skills/code-review/`, imported from Claude Code | the skill, for Claude Code and for Codex |
| the skill `skills/release-notes/`, written by you | the skill, for Claude Code and for Codex |
| the MCP servers `memory` and `docs` in `canonfig.jsonc` | those servers in `~/.claude.json` and `~/.codex/config.toml`; every other key in those files stays |

The examples assume Claude Code on A already has a `code-review` skill and a
`memory` MCP server. Setup shows what your Claude Code holds, and you import
that instead.

## Before you start

- **Node.js 24 or newer and npm** on both machines, installed for the user
  account you run Claude Code and Codex under. Get Node.js from
  [nodejs.org](https://nodejs.org/en/download) or your package manager.
- **Linux or macOS with a POSIX shell.** The commands below use one. For
  Windows, see [Platform differences](/reference/cross-platform).
- **Claude Code and Codex installed on both machines.** Canonfig detects them
  and manages their configuration. It does not install them.
- **SSH from B to A.** The Source Machine listens only on its own loopback
  address, so B reaches it through an SSH tunnel that Canonfig manages. You
  need an SSH login on A and A's SSH host public key. If A and B are two user
  accounts on one host, you need no SSH.
- **The same Canonfig release on both machines.** A Source Machine and a
  Follower Machine on different `major.minor` releases refuse to talk to each
  other.

The examples use `a.example` and `b.example` as host names and `maria` as the
user on both machines. Replace them with your own.

<Callout title="Canonfig replaces what it manages" type="warning">
  The first time Canonfig writes to a harness, it copies the files it is about
  to manage into a Takeover Snapshot, then replaces them. Afterward,
  `~/.claude/skills/` holds exactly the skills in your folder. Anything you do
  not import in step 2 leaves the harness and stays only in the snapshot.
</Callout>

## 1. Install Canonfig on both machines

Run on A and on B:

```bash
npm install --global @microck/canonfig@7.1.6
canonfig --version
canonfig doctor --no-input
```

`canonfig --version` prints `7.1.6`. `doctor` prints one line per check. Look
at the `credentials` line: Canonfig keeps its keys in the system credential
store (Secret Service on Linux, Keychain on macOS). If that line reports a
problem, follow the fix it prints, or see
[Run Canonfig unattended](/how-to/run-unattended), before you continue.

## 2. Set up machine A as the Source Machine

Setup creates the Source Machine's keys and the folder, and offers to import
what Claude Code and Codex already hold. Nothing changes until you approve the
plan and apply it.

On A, plan the setup:

```bash
canonfig setup plan --role source
```

Setup detects which harnesses are installed and lists them. Among the
decisions in the output you see:

```text
AI coding tools selected from detection: codex, claude-code.
Installed AI coding tools found: codex, claude-code.
```

To manage a different set, name each harness with `--harness`, for example
`--harness claude-code --harness codex --harness opencode`.
[Choose which harnesses Canonfig manages](/how-to/choose-harnesses) explains
detection.

The plan also lists, under `imports`, every instruction file, rule, skill,
subagent, command, and MCP server those harnesses hold. Each one has an `id`,
such as `claude-code/skills/code-review`, and the `target` it would become in
`~/.canonfig/`. The plan imports none of them until you choose.

Import everything Claude Code holds:

```bash
canonfig setup plan --role source --import claude-code
```

`--import` takes a harness, as here, or one item's `id`, and you can repeat
it. `--import-all` takes every item, and `--no-import` reads no harness files
at all. When two harnesses hold different items with the same name, for
example Claude Code's `CLAUDE.md` and Codex's `AGENTS.md`, the plan lists an
`import collision` under `exclusions` and imports neither until you name one
by its `id`. An MCP value that looks like a credential becomes a `fromEnv`
reference when it is imported, and the plan lists each one.

Approve the plan, then apply it:

```bash
canonfig setup approve --approver "$USER"
canonfig setup apply
```

`setup apply` creates the Source Machine's signing key and TLS identity, then
`~/.canonfig/` with `canonfig.jsonc`, `AGENTS.md` (Claude Code's `CLAUDE.md`),
and `skills/code-review/`, and adds the `memory` MCP server to
`canonfig.jsonc`. Nothing is written to Claude Code or Codex yet.

## 3. Write your folder

Open `~/.canonfig/canonfig.jsonc`. Setup wrote the harness list, the imported
MCP server, and a `profile`, which names what the Source Machine publishes.
Setup takes the profile from the machine's hostname; this tutorial renames it
to `workstation`. Add a second MCP server whose token comes from an
environment variable:

```jsonc title="~/.canonfig/canonfig.jsonc"
{
  "version": 1,
  "profile": { "id": "workstation", "name": "Workstation" },
  "harnesses": ["codex", "claude-code"],
  "mcp": {
    "memory": {
      "transport": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-memory"]
    },
    "docs": {
      "transport": "streamable-http",
      "url": "https://mcp.context7.com/mcp",
      // Each harness reads the token from its own environment when it starts.
      "headers": { "CONTEXT7_API_KEY": { "fromEnv": "CONTEXT7_API_KEY" } }
    }
  }
}
```

Never write a token itself into the folder. Publishing refuses a value that
looks like a credential. `{ "fromEnv": "NAME" }` becomes each harness's own
environment reference, so every machine supplies its own token.

Add a line to `~/.canonfig/AGENTS.md`, the instructions every harness reads:

```markdown title="~/.canonfig/AGENTS.md"
Run the test suite before you say a change is done.
```

Add a skill. The directory name and the `name` in `SKILL.md` must match:

```markdown title="~/.canonfig/skills/release-notes/SKILL.md"
---
name: release-notes
description: Write release notes from the commits since the last tag.
---

List the commits since the last tag with `git log --oneline $(git describe --tags --abbrev=0)..HEAD`.
Group them into Added, Changed, and Fixed, and leave out internal changes.
```

The [Canonical Folder reference](/reference/canonfig-folder) lists every key
and file the folder can hold.

## 4. Preview, then project on machine A

On A:

```bash
canonfig sync --plan
```

The plan names each harness and its root, and one `takeover` line per harness
listing the surfaces Canonfig takes over and whether it keeps a backup, for
example:

```text
harnesses:
  codex          /home/maria/.codex
  claude-code    /home/maria/.claude
takeover: claude-code (/home/maria/.claude): instructions, skills, mcp#mcpServers; takeover snapshot
```

Then it lists one action per harness surface. Nothing changes yet. When the
plan matches what you expect, apply it:

```bash
canonfig sync --apply
```

Canonfig copies the current content of every surface it takes over into
`~/.canonfig/.backups/`, prints the snapshot's name on a
`takeover snapshot:` line, writes the projection, and checks every surface.
The result ends with `outcome: Converged`. If a surface fails, Canonfig rolls
the run back and names the surface and the reason; see
[Recover from a failed or blocked sync](/how-to/recover).

Run `canonfig sync --apply` a second time. It reports
`outcome: Converged` with no actions and takes no snapshot. To undo the
takeover, see [Restore a harness from a backup](/how-to/restore-from-a-backup).

## 5. Publish

On A:

```bash
canonfig source publish --reviewer "$USER"
```

The output starts with `source.publish completed`, then names the profile and
sequence number, and lists one resource per item in the folder:

```text
source.publish completed
profile: workstation, sequence 1
```

`--reviewer` is required and records who approved the Profile Revision.
Publishing the same content again returns the same Profile Revision; changed
content becomes the next sequence number. Only the folder's authoring entries
are published: `canonfig.jsonc`, `AGENTS.md`, `rules/`, `skills/`, `agents/`,
`commands/`, and `hooks/`.

## 6. Keep the Source Machine serving

B fetches Profile Revisions from A, so A must be serving whenever B syncs. On
A, install the user service:

```bash
canonfig source service install
canonfig source service status
```

`install` returns once A answers on `https://127.0.0.1:17342`. `status`
reports `running`. The service is a systemd user unit
(`canonfig-source.service`) on Linux and a LaunchAgent (`dev.canonfig.source`)
on macOS, and it runs while you are logged in. On macOS, run `install` from the
desktop session, not over SSH. To keep A serving after logout or reboot, see
[Run Canonfig unattended](/how-to/run-unattended).

## 7. Invite machine B

On A:

```bash
canonfig source invite --endpoint https://127.0.0.1:17342 --output ~/canonfig-invite --expires 1h
```

The command writes `~/canonfig-invite`. The invitation works once and expires
after one hour (without `--expires`, after 15 minutes; at most 24 hours).
Treat it like a password until B has enrolled. Copy it to B, together with
A's SSH host public key read from A's own disk:

```bash
scp ~/canonfig-invite b.example:canonfig-invite
scp /etc/ssh/ssh_host_ed25519_key.pub b.example:source-host-key.pub
```

## 8. Enroll machine B

On B, start the tunnel to A. Skip this command if A and B are the same host.

```bash
canonfig tunnel start --invitation ./canonfig-invite --ssh-host a.example --ssh-user maria --ssh-host-key-file ./source-host-key.pub
```

The tunnel forwards B's `127.0.0.1:17342` to A over SSH, and checks A's SSH
host key, TLS certificate, and signing key against the values you supplied.
Canonfig records the tunnel, so later you restart it with
`canonfig tunnel start` alone.

Enroll B, then delete the invitation. The invitation goes through a pipe,
never as an argument:

```bash
cat ./canonfig-invite | canonfig follower enroll --stdin --name laptop
rm ./canonfig-invite
```

B trusts only the Source Machine named in the invitation, stores its own
credential in its credential store, and follows the profile A publishes.
`canonfig status` shows the trusted signing and TLS fingerprints.

On a Follower Machine, `~/.canonfig/` holds a mirror of what the Source
Machine publishes, so enrollment refuses a folder that already holds authored
items. If B has its own `~/.canonfig/canonfig.jsonc` or skills, see the table
at the end of this page.

## 9. Preview, then apply on machine B

On B:

```bash
canonfig sync --plan
```

The plan starts with the Profile Revision it fetched, then shows the same
`harnesses` and `takeover` lines as on A, this time for B's own harness files.
A harness the profile lists but B does not have installed appears on a
`not installed (listed, not projected)` line and does not stop the run. When
the plan matches what you expect, apply it:

```bash
canonfig sync --apply
```

Canonfig mirrors the published items into B's `~/.canonfig/`, takes a Takeover
Snapshot of B's harness files, projects the mirror, and checks every surface.
The result is `outcome: Converged`. Run `canonfig sync --apply` again: it
reports `Converged` with no actions.

## 10. Check each harness

`Converged` means the files are in place and verified. Each harness still
decides what it trusts, and Canonfig does not copy those decisions:

- **Claude Code.** Restart Claude Code and run `/mcp` to see the `memory` and
  `docs` servers. Set `CONTEXT7_API_KEY` in the environment Claude Code starts
  from, or the `docs` server cannot authenticate.
- **Codex.** Run `codex mcp list` to see both servers. Codex asks you to trust
  each project directory the first time and stores that decision in
  `~/.codex/config.toml`. Canonfig changes only the MCP keys in that file, so
  the decision survives later syncs.

When an apply writes something a harness asks you to review, such as hooks,
the output ends with "still to do in each client" and names the review.

## 11. Sync B every day

On B:

```bash
canonfig schedule set daily@09:00
canonfig schedule status
```

`schedule set` prints the time zone it used and the next run time.
`schedule status` reports `current`. At 09:00 each day, a systemd user timer
(Linux) or launchd agent (macOS) runs
`canonfig sync --apply --no-input --scheduled`. No Canonfig process runs in
between.

The schedule runs only when the machine can run it:

- **Linux:** while you are logged in, unless you turn on lingering with
  `loginctl enable-linger "$USER"`.
- **macOS:** while you are logged in to the desktop with the login Keychain
  unlocked.

[Sync on a schedule](/how-to/manage-schedules) covers time zones, daylight
saving time, and missed runs.

After the first scheduled run, check B:

```bash
canonfig status
```

`applied` and `independentlyVerified` read `verified`, and `scheduled` reads
`verified` once a scheduled run has completed. If the last scheduled run
failed, `status` shows the reason.

## 12. Change something and watch it arrive

On A, edit `~/.canonfig/AGENTS.md`, then project and publish again:

```bash
canonfig sync --apply
canonfig source publish --reviewer "$USER"
```

The publish output shows `sequence 2`. B applies it at its next scheduled run,
or immediately when you run `canonfig sync --apply` on B.

To stop sharing an item, delete it from the folder and publish. B removes what
Canonfig wrote for it, as long as nobody changed it on B. Canonfig never
removes installed tools or local credentials.

Do not edit B's mirror in `~/.canonfig/`. A changed mirror file is Follower
Drift: Canonfig keeps your edit, reports it, and stops updating that item's
projections. To add something to B only, use its local folder; see
[Add items to one machine only](/how-to/add-machine-local-items).

## If a step fails

| Message | Cause | Fix |
| --- | --- | --- |
| "unknown harness: claude" (`setup plan`, exit 2) | `--harness` takes a harness id. | Use an id such as `claude-code`; the message lists every id. |
| "import collision: AGENTS.md differs between claude-code/instructions/AGENTS.md, codex/instructions/AGENTS.md; choose one with --import &lt;id&gt;" (under `exclusions`) | Two harnesses hold different instructions. | Plan again and add `--import` with the `id` you want to keep. |
| `/home/maria/.canonfig/canonfig.jsonc needs "profile": { "id": ..., "name": ... } to publish; the id names the Machine Profile followers sync` (`source publish`, exit 2) | `canonfig.jsonc` has no `profile`. Setup writes one, so it was removed. | Add `"profile": { "id": "workstation", "name": "Workstation" }`, as in step 3. |
| "... contains a literal credential [REDACTED]; remove the value and use a symbolic environment reference ..." (`source publish`, exit 2) | A value in `canonfig.jsonc` looks like a secret. | Replace it with `{ "fromEnv": "NAME" }`. |
| "/home/maria/.canonfig already holds authored items (canonfig.jsonc, skills), where a follower keeps its Source's mirror; ..." (`follower enroll`, exit 2) | B's `~/.canonfig/` holds its own items. | Move what B should keep into `~/.canonfig/local/` (see [Add items to one machine only](/how-to/add-machine-local-items)) or remove it, then enroll again. |
| "this machine is a Source (signing key ...), so it cannot enroll as a Follower: a machine is either a Source or a Follower, never both. ..." (`follower enroll`, exit 2) | You ran the enrollment on A, or B was made a Source earlier. A machine holds one role. | Enroll on B. If B should stop being a Source, run `canonfig source service remove` on B, move B's `~/.canonfig/` aside, then enroll again. The invitation is still valid. |
| "this machine follows the Source at https://127.0.0.1:17342 (signing key ...) as laptop (...), so it cannot publish a revision: ..." (`source init`, `source publish` and the other `source` commands, exit 2) | You ran a Source command on B. | Run it on A. To make B a Source instead, run `canonfig follower unenroll` on B first. |
| "Invitation duration must not exceed 24h" (`source invite`, exit 2) | `--expires` is longer than 24 hours. | Pick a value such as `15m`, `1h`, or `24h`. |
| "This invitation has expired. Create a new invitation on the Source and try again." (exit 5) | B used the invitation after its `--expires` time. | Run `canonfig source invite` on A again, copy the file, and enroll with it. |
| "This invitation has already been used. Create a new invitation on the Source and try again." (exit 5) | Each invitation enrolls one machine once. | Issue another invitation on A. |
| "The Source's certificate fingerprint does not match this invitation." | B reached a server whose TLS certificate is not the one in the invitation: another Source Machine on the same port, or an invitation from an earlier setup. | On A, run `canonfig source service status` to confirm which Source Machine is serving, then issue an invitation from it. Do not enroll until the fingerprints match. |
| "SSH host identity for a.example did not match its pin" (`tunnel start`) | The host key file does not belong to the host you connected to. | Copy `/etc/ssh/ssh_host_ed25519_key.pub` from A again, reading it on A itself, and check that `--ssh-host` names A. |
| "nothing answered at the Source endpoint" (exit 6) | Nothing listens on `127.0.0.1:17342`: A is not serving, or the tunnel is down. | On A, run `canonfig source service status` and expect `running`. On B, run `canonfig tunnel status`, then `canonfig tunnel start`. If A serves on another port, use that port in `--endpoint` and in `tunnel start --local-port`. |
| "source/follower version mismatch" (exit 2) | A and B run different `major.minor` releases. The message names both. | Install the same release on both machines, as in step 1. |
| "the follower identity is already enrolled" | A Follower Machine named `laptop` is already enrolled. | Pick another `--name`, or revoke the old one on A first with `canonfig source revoke`. |

For other errors, run `canonfig doctor --no-input` on the machine that failed.
[Doctor probes and exit codes](/reference/diagnostics) lists every check.
