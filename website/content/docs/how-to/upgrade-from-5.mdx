---
title: Upgrade from Canonfig 5.0.1
description: What this release keeps from a 5.0.1 Source or Follower Machine, what it refuses, and how to get past a refusal.
---

You do not reinitialize a machine to upgrade it. The first `canonfig` command
you run after installing this release reads the state that 4.0.0 through 5.0.1
wrote in `~/.canonfig/state.sqlite` and carries it forward in one step.

## What happens on the first run

1. Canonfig checks every stored item first. If one has no equivalent in this
   release, it stops, names the item and the step that fixes it, and changes
   nothing. See [When the upgrade refuses](#when-the-upgrade-refuses).
2. It copies the whole database to
   `~/.canonfig/state-before-format-6-<UTC time>.sqlite`, readable only by you.
3. It upgrades the database in one transaction and records what it changed in
   the `state_upgrades` table of the same database.

Later runs find the upgraded state and do nothing more.

## What carries over

- **Enrollment.** The Source identity and keys, enrolled followers, follower
  credentials, groups and invitations stay as they were. Followers keep
  talking to the Source without a new invitation.
- **Run history.** Every run, journal entry, drift record, deployment receipt
  and publication approval stays.
- **Schedules and secrets.** A follower's schedule choice and the names of
  shared secrets stay. Secret values never left the credential store.
- **Tools and credentials.** A follower's record of each tool it installed
  and each credential it checked stays as it was.
- **Published revisions.** A Source keeps every revision it published, with
  its profile and sequence. This release cannot apply their resources, so
  publish from `~/.canonfig/` once on the Source after upgrading; the new
  revision continues the sequence under the same profile id.

Canonfig stops managing the `file`, `directory`, `config` and `skill`
resources 5.0.1 applied, and lists each one in `state_upgrades`. Their files
and keys stay exactly where they are. When the Source authors those paths
again, through the folder or as a `resources` entry (see
[Manage files outside harnesses](/how-to/manage-files-outside-harnesses)),
the next sync takes them over like any other harness file and backs them up
first. Local Overlay keys are dropped and listed too; they stay in the file as
the follower's own keys.

## When the upgrade refuses

The message names the item, the reason, and the recovery. The state is not
changed and no copy is written.

| Item | Recovery |
| --- | --- |
| A run 5.0.1 left unfinished | Install 5.0.1 again, run `canonfig recover` or `canonfig abandon`, then install this release. |
| A Source that published more than one profile | Keep that Source on 5.0.1, or move the database aside and set the machine up again as the Source of one profile. Publishing several profiles from one Source is tracked in [issue #254](https://github.com/Microck/canonfig/issues/254). |

State from a release before 4.0.0 needs one run of 5.0.1 first, for example
`npx @microck/canonfig@5.0.1 status`.

To go back to 5.0.1 after an upgrade, install 5.0.1 and move the
`state-before-format-6-*.sqlite` copy to `~/.canonfig/state.sqlite`.
