---
title: Upgrade Canonfig
description: Move the Source Machine and every Follower Machine to another Canonfig release without breaking synchronization.
---

After these steps, the Source Machine and every Follower Machine run the same
release and sync again. From 4.x, enrollments, Profile Revisions, credentials,
and schedules carry over. From 3.2.x, nothing carries over: you set up a
separate Source Machine and Follower Machines instead.

## Which releases work together

A Source Machine and a Follower Machine must run the same `major.minor`
release. Patch releases of one line, such as 5.0.0 and 5.0.1, work together.
A 5.0.x Source Machine refuses a 4.x Follower Machine, and a 5.0.x Follower
Machine refuses a 4.x Source Machine. Synchronization stops between two
machines on different lines until both are upgraded, so upgrade every machine
in one maintenance window:

1. Pause the schedule on every Follower Machine.
2. Upgrade the Source Machine.
3. Upgrade each Follower Machine.
4. Resume the schedules.

## Upgrade from 4.x

### Before you start

- Finish every open run with the build that started it. On each Follower
  Machine, run `canonfig status`. If it reports an interrupted run, run
  `canonfig recover` before you replace the package. See
  [Recover from a failed or blocked sync](/how-to/recover).
- Back up `~/.canonfig` and note where the installed package lives. Keep the
  backup private: it holds enrollment and transport details. The backup does
  not include items in the system credential store.

### 1. Pause the schedules

On each Follower Machine:

```bash
canonfig schedule status
canonfig schedule remove
```

Write down the schedule `status` reports, so you can set it again in step 4.

### 2. Upgrade the Source Machine

Install into the same npm prefix as the existing installation, then check it:

```bash
npm install --global @microck/canonfig@5.0.0
canonfig --version
canonfig doctor --no-input
```

A running Source Machine keeps serving the old build until you restart it.
Restart the service you already have, keeping its host, port, and environment:

- **Linux:** `systemctl --user restart canonfig-source.service`
- **macOS:** from the desktop session, `launchctl kickstart -k gui/$(id -u)/dev.canonfig.source`
- **Windows:** end and run the Task Scheduler task `Canonfig\canonfig-source`.

If you run `canonfig source serve` in a terminal instead, stop it and start it
again with the same `--host` and `--port`.

Then confirm it serves:

```bash
canonfig source service status
```

The output reports `running` and `serving: true`.

### 3. Upgrade each Follower Machine

On each Follower Machine, install into the same prefix and preview a sync:

```bash
npm install --global @microck/canonfig@5.0.0
canonfig --version
canonfig doctor --no-input
canonfig sync --plan
```

When the plan matches what you expect, apply it:

```bash
canonfig sync --apply
```

The result is `Converged`.

### 4. Resume the schedules

On each Follower Machine, set the schedule you wrote down in step 1, for
example:

```bash
canonfig schedule set daily@09:00
canonfig schedule status
```

`schedule status` reports `current`. Keep the backup until every machine
reports `Converged`.

## Move from 3.2.x

You cannot upgrade a 3.2.x installation in place, and nothing migrates from
it. The signed Profile Revision format differs, so Profile Revisions,
enrollments, credentials, and schedules do not carry over. You set up a
separate Source Machine and Follower Machines and leave the 3.2.x installation
untouched.

<Callout type="warn">
  Do not install 5.0.0 into the npm prefix of a 3.2.x installation, and do not
  point it at the 3.2.x state directory. Doing so replaces the package the old
  installation runs. Leave the existing package, state directory, service,
  schedules, and credential items untouched while setting up 5.0.0.
</Callout>

1. On each 3.2.x machine, record the installed version, role, profile, and
   schedule. If the old `canonfig` command does not start, record the package
   metadata instead and leave the installation as it is.
2. Back up each machine's `~/.canonfig`, the installed package, and the profile
   file with the files it references. Store each machine's backup separately
   and privately. The backup does not include items in the system credential
   store, so keep the old user account intact.
3. Use a separate machine, or a separate user account with its own npm prefix.
   On Linux or macOS, as that account:

   ```bash
   npm install --global --prefix "$HOME/.local" @microck/canonfig@5.0.0
   export PATH="$HOME/.local/bin:$PATH"
   canonfig --version
   ```

   Check that `canonfig` resolves to `$HOME/.local/bin/canonfig`. On Windows,
   follow the [Windows installation steps](https://github.com/Microck/canonfig/blob/main/skills/install-canonfig/references/windows.md).
4. Copy the profile file and the files it references to that account, leaving
   out secrets and keeping the relative paths the same.
5. Follow [Sync your first two machines](/tutorials/first-sync) from step 2 to
   create a Source Machine with its own identity, publish the profile, and
   enroll each Follower Machine with its own invitation. If the 3.2.x Source
   Machine runs on the same host, give the 5.0.0 Source Machine another port
   with `canonfig source service install --host 127.0.0.1 --port 17343`, and
   use that port in the invitation endpoint and in
   `canonfig tunnel start --local-port`.

## If something fails

| Message | Cause | Fix |
| --- | --- | --- |
| "source/follower version mismatch: source 4.2.0 vs follower 5.0.0" (exit 2) | The two machines run different `major.minor` releases. | Upgrade the machine on the older line. |
| "run `<id>` was created by canonfig 4.2.0 ... finish the run with the creating build or set CANONFIG_ACCEPT_FOREIGN_BUILD=1 to accept the upgrade" (exit 4) | The machine has an open run from the previous build. | Reinstall the version the message names, run `canonfig recover`, then upgrade again. Set `CANONFIG_ACCEPT_FOREIGN_BUILD=1` only if you cannot reinstall that build and accept that the upgraded build finishes a run it did not start. |
| "a revision published by an earlier canonfig release cannot be served; publish the profile again on the Source Machine" | The Source Machine holds a Profile Revision the upgraded release cannot serve. | On the Source Machine, run `canonfig source publish --profile-file ~/canonfig.profile.jsonc --reviewer "$USER"`, then sync again. |
| "the gemini agent harness was removed in 5.0.0; run 'canonfig agent harness codex\|claude\|custom ...' to replace it" (exit 2) | The Follower Machine still has a `gemini` agent harness configured. | Set another harness, for example `canonfig agent harness codex --executable /usr/local/bin/codex`, then sync again. See [Let a Configuration Agent resolve work](/how-to/configure-agent-policies#replace-a-gemini-harness). |
| `canonfig source service status` does not report `serving: true` | The service did not restart, or it cannot read its keys. | Restart it as in step 2 and run `canonfig doctor --no-input`. Follow the fix its `credentials` and `source` lines print. |
