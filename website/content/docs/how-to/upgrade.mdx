---
title: "How-to: upgrade to Canonfig 5.0.0"
description: Move the Source Machine and every Follower Machine to Canonfig 5.0.0 without breaking synchronization.
---

When you finish, the Source Machine and every Follower Machine run 5.0.0 and
sync again. Existing enrollments, revisions, credentials, and schedules carry
over when you upgrade from 4.x. From 3.2.x you set up a separate
5.0.0 fleet instead.

## Upgrade the whole fleet together

A Source Machine and a Follower Machine must run the same `major.minor`
release. A 5.0.0 Source Machine refuses a 4.x follower, and a 5.0.0 follower
refuses a 4.x Source Machine. Synchronization stops between any two machines
on different lines until both are upgraded, so plan one maintenance window for
the whole fleet:

1. Pause the schedule on every Follower Machine.
2. Upgrade the Source Machine.
3. Upgrade each Follower Machine.
4. Resume the schedules.

Patch releases within one line (for example 5.0.0 and 5.0.1) work together.

## Upgrade from 4.x

Before you start:

- Finish every unfinished run with the build that started it. On each Follower
  Machine, run `canonfig status`; if it reports an interrupted run, run
  `canonfig recover` before you replace the package. See
  [Recover](/how-to/recover).
- Back up `~/.canonfig` and note where the current package is installed. Keep
  the backup private: it holds enrollment and transport details. The backup
  does not include items in the system credential store.

### 1. Pause follower schedules

On each Follower Machine:

```bash
canonfig schedule status
canonfig schedule remove
```

Write down the schedule `status` reports so you can set it again in step 4.

### 2. Upgrade the Source Machine

Install 5.0.0 into the same npm prefix as the existing installation, then
check it:

```bash
npm install --global @microck/canonfig@5.0.0
canonfig --version
canonfig doctor --no-input
```

A running Source Machine keeps serving the old build until you restart it.
Restart the service you already have, keeping its host, port, and environment:

- **Linux:** `systemctl --user restart canonfig-source.service`
- **macOS:** from the desktop session, `launchctl kickstart -k gui/$(id -u)/dev.canonfig.source`
- **Windows:** end and run the Task Scheduler task `Canonfig\canonfig-source`.

If you run `canonfig source serve` in a terminal instead, stop it and start it
again with the same `--host` and `--port`.

Then confirm it serves:

```bash
canonfig source service status
```

The output reports `running` and `serving: true`.

### 3. Upgrade each Follower Machine

On each Follower Machine, install into the same prefix and preview a sync:

```bash
npm install --global @microck/canonfig@5.0.0
canonfig --version
canonfig doctor --no-input
canonfig sync --plan
```

When the plan matches what you expect, apply it:

```bash
canonfig sync --apply
```

The result is `Converged`.

### 4. Resume schedules

On each Follower Machine, set the schedule you wrote down in step 1, for
example:

```bash
canonfig schedule set daily@09:00
canonfig schedule status
```

Keep the backup until every machine reports `Converged`.

## Move from 3.2.x

You cannot upgrade a 3.2.x installation in place, and nothing migrates from
it: the signed revision format changed, so revisions, enrollments, credentials,
and schedules do not carry over. Instead, you build a separate 5.0.0 fleet and
leave the 3.2.x installation untouched.

<Callout type="warn">
  Do not install 5.0.0 into the npm prefix of a 3.2.x installation, and do not
  point it at the 3.2.x state directory. Doing so replaces the package the old
  installation runs. Leave the existing package, state directory, service,
  schedules, and credential items untouched while setting up 5.0.0.
</Callout>

1. On each 3.2.x machine, record the installed version, role, profile, and
   schedule. If the old `canonfig` command no longer starts, record the
   package metadata instead and leave the installation as it is.
2. Back up each machine's `~/.canonfig`, the installed package, and the profile
   file with the files it references. Store each machine's backup separately
   and privately. The backup does not include items in the system credential
   store, so keep the old user account intact.
3. Use a separate machine, or a separate user account with its own npm prefix.
   On Linux or macOS, as the new account:

   ```bash
   npm install --global --prefix "$HOME/.local" @microck/canonfig@5.0.0
   export PATH="$HOME/.local/bin:$PATH"
   canonfig --version
   ```

   Check that `canonfig` resolves to `$HOME/.local/bin/canonfig`. On Windows,
   follow the [Windows installation steps](https://github.com/Microck/canonfig/blob/main/skills/install-canonfig/references/windows.md).
4. Copy the profile file and the files it references to the new account,
   leaving out secrets and keeping the relative paths the same.
5. Follow [the first-sync tutorial](/tutorials/first-sync) from step 2 to
   create a Source Machine with a new identity, publish the profile, and enroll
   each follower with a new invitation. If the old Source Machine runs on the
   same host, give the new one another port with
   `canonfig source service install --host 127.0.0.1 --port 17343` and use that
   port in the invitation endpoint and in `canonfig tunnel start --local-port`.

## If something fails

**Sync or enrollment fails with `source/follower version mismatch: source 4.2.0 vs follower 5.0.0`.**
The two machines run different `major.minor` releases. The message names both
versions. Upgrade the machine on the older line.

**A command fails with `run <id> was created by canonfig 4.2.0 ... finish the run with the creating build or set CANONFIG_ACCEPT_FOREIGN_BUILD=1 to accept the upgrade`.**
The machine has an unfinished run from the previous build. Reinstall the
version the message names, run `canonfig recover`, then upgrade again. Set
`CANONFIG_ACCEPT_FOREIGN_BUILD=1` only if you cannot reinstall that build and
accept that 5.0.0 finishes a run it did not start.

**Sync fails with `a revision published by an earlier canonfig release cannot be served; publish the profile again on the Source Machine`.**
The Source Machine holds a revision the upgraded release cannot serve. On the
Source Machine, run
`canonfig source publish --profile-file ~/canonfig.profile.jsonc --reviewer "$USER"`,
then sync again.

**Sync fails with `the gemini agent harness was removed in 5.0.0; run 'canonfig agent harness codex|claude|custom ...' to replace it`.**
The Follower Machine still has the removed Gemini agent harness configured.
Choose another harness, for example
`canonfig agent harness codex --executable /usr/local/bin/codex`, then sync
again. See [Configure agent policies](/how-to/configure-agent-policies).

**`canonfig source service status` does not report `serving: true` after the upgrade.**
The service did not restart, or it cannot read its keys. Restart it as in step
2 and run `canonfig doctor --no-input`; follow the fix its `credentials` and
`source` lines print.
